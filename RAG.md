# RAG

**RAG (Retrieval-Augmented Generation)** is a framework that combines retrieval-based methods with generative models to improve the quality and relevance of generated content. By using external knowledge sources, RAG can give more accurate and contextually appropriate responses in applications such as question answering, summarization and conversational AI.

Imagine you have a question about a specific topic, and you want an answer that is not only generated by a language model but also informed by relevant documents or data. RAG retrieves relevant information from a knowledge base and uses it to generate a more informed response.

## The Flow

Chunking → Embedding → Vector Database → Semantic Search → Caching → Generation

## Security and Restrictions

When using RAG, consider the security and privacy implications:

- Make sure the external knowledge sources you use are reliable and secure.
- Avoid exposing sensitive information during retrieval.
- Implement proper access controls to protect confidential data.

## Fine-tuning vs. RAG

Fine-tuning means training a model further on a specific dataset to improve its performance for a particular task or domain. The model learns from relevant examples and adapts its responses accordingly.

**Example:** you want the model to know the company's privacy policy. Policies change constantly, so you would have to retrain the model every time. This is slow and expensive, and the model can still give outdated or inaccurate answers.

**RAG is the better solution here.** Keyword search is also not efficient for finding the right information in a privacy policy, because the exact words in the question often differ from the words in the document. RAG retrieves by meaning, and when a policy changes you only update the documents in the vector database, with no retraining.

## Semantic Search

Semantic search goes beyond traditional keyword-based search. Instead of relying only on exact keyword matches, it understands the **meaning and context** of the query and retrieves more relevant results. Using natural language processing (NLP) and machine learning, it can identify synonyms, related concepts and contextual relationships between words.

In NLP there are sentence-similarity models such as **all-MiniLM-L6-v2**, which works well for semantic search. It maps sentences and paragraphs to a **384-dimensional dense vector space**. This model is much smaller than GPT-3.5 or GPT-4.

> Semantic search works mainly on text.

## Vectors and Embedding

An embedding model converts each word (or sentence) into a vector of numbers. Words with related meanings, like "work" and "office", get numbers that are close to each other. When the vectors are plotted, vectors that are close together are similar in meaning.

## Vector Database

When searching across many huge files, vectors are the solution. A vector database can search through many documents and return results in seconds. It is also used for semantic search, because it can find the similarity between words and sentences.

Vector database options:

- Dedicated: **Chroma**, **Pinecone**, **Weaviate**
- Extensions of existing databases: **PostgreSQL** (pgvector), **MySQL**, **MongoDB**

> **Note:** Chroma can run in-memory, in which case the data is lost when the process ends. For production, use persistent storage (a persistent client with a disk volume, or cloud storage such as S3, GCP or Azure Blob Storage).

## Chunking

Chunking is the process of breaking large documents into smaller, manageable pieces called **chunks**. It makes retrieval and processing more efficient in RAG and semantic search, because the model can focus on specific sections of a document, which improves the relevance and accuracy of the answers.

There are several chunking methods:

- Sentence chunking
- Paragraph chunking
- Sliding window chunking

The choice depends on the use case and the nature of the text.

### Guidelines

- **Size:** roughly 200 to 500 words per chunk, depending on the complexity of the content and the retrieval requirements. Smaller chunks give more precise retrieval, while larger chunks give the model more context.
- **Boundary rules:** split at sentence boundaries or paragraph breaks so chunks keep a coherent meaning. Avoid splitting in the middle of sentences or phrases, because this loses context and reduces retrieval accuracy.
- **Quality checks:** test with real queries to make sure the retrieved chunks are relevant to the user's needs. Adjust the chunking strategy based on the results.

## Caching with Redis

RAG can be slow because every query needs to search the vector database (and call the LLM). Caching solves this by storing results in memory. The next time the same query comes in, the result is returned from the cache instead of being computed again.

There are four levels of caching:

| Cache | What is stored | Why it helps |
|---|---|---|
| **Chunk caching** | The complete chunking result of a document | Avoids re-chunking the same document. |
| **Embedding caching** | The computed vectors for a text | Generating embeddings is expensive, so reuse them. |
| **Vector (search) caching** | The results of vector database queries | Searching the vector database is expensive. |
| **LLM response caching** | The generated answer for a query | The LLM is the slowest and most expensive part of RAG, so this gives the biggest gain. |

## Monitoring

Monitoring is essential for keeping a RAG system performant and reliable. It means tracking metrics to make sure the system works as expected and to spot problems early. This allows proactive maintenance, optimization and troubleshooting, so the system keeps delivering accurate and relevant results.

What to monitor in the pipeline:

- **Retrieval quality:** how relevant the returned chunks are to the user's questions.
- **Embedding performance:** how long it takes to generate vectors.
- **Chunking efficiency:** how well documents are being split.

System-level metrics:

- **Response time**
- **Throughput** (queries per second)
- **Error rate**

Monitoring these metrics helps to identify bottlenecks, optimize performance and make sure the system meets its service level agreements (SLAs).
